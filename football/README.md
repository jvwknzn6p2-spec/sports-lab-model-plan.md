# football — サッカーの台帳（リポジトリ内・追記専用）

`.github/workflows/football-daily.yml` が毎日 07:05 JST（着地は遅れて 12:00 前後）に更新する。実装は
`lib/football-model/src/ledger.ts`（台帳）と `src/cli/football.ts`（日次）。

| パス | 中身 |
|---|---|
| `ledger/matches.ndjson` | 日程（The Odds API 由来・providerId ごとに最新行が有効） |
| `ledger/predictions.ndjson` | 予想（1 試合 1 行・封緘＝試合日（JST）の前日 20:00 JST より前に発行・以後不変。2026-09-08 以前の行は旧規則 kickoff−60 分の cutoffAt を持つ） |
| `ledger/results.ndjson` | 結果（直近 30 日ぶん・`source` に取得元） |
| `ledger/evaluations.ndjson` | 決済（RPS / Brier / log loss・市場 RPS） |
| `market/<sport>/<取得時刻>.json` | 発行に使った市場確率の写し（取得時刻つき） |
| `reports/summary.md` | 要約（人が読む場所） |
| `history/<Div>.ndjson` | 結果の履歴（学習データの権威・2022-04 以降・1 試合 1 行・取得元と取得時刻つき） |

規則: 台帳のファイルは**手で編集しない・削除しない**。訂正が要るときは行を追記する。
`cache/` は取得の一時置き場で commit しない。`history/` は日次が差分で更新する
（行の置換はあるが、同じか高い優先度の取得元からしか起きない。`src/history.ts`）。

## 結果の取得元は 3 つ・履歴が権威（2026-09-09）

2026-09-06〜09 に football-data.co.uk（`www.` ホスト）が Actions に HTTP 503 を返し、
cache を commit しない設計では学習データが丸ごと消えて **4 日間 予想が 1 件も出なかった**。
「予想は試合前に必ず出す」（Founder 指示 2026-09-09）を取得元の生死から切り離すため、
結果を `history/` に持ち、毎日の取得は差分の取り込みにした。

| 優先度 | 取得元 | 中身 | 欠けたとき |
|---|---|---|---|
| 3 | football-data.co.uk（`https://football-data.co.uk/…`・www. 無しを先に） | 一次情報・現地日付・B365 オッズ | 他の 2 つと履歴で進む |
| 2 | GitHub の写し `xgabora/Club-Football-Match-Data-2000-2025`（`data/Matches.csv`） | football-data.co.uk 由来で名前も同じ。更新は不定期（2026-09-09 時点で 9/3 まで） | 同上 |
| 1 | The Odds API `scores?daysFrom=3`（2 クレジット/競技） | 結果の速報（UTC のキックオフ日付・オッズ無し）。未決済の予想があり開始 2 時間〜3 日の競技だけ要求する | 同上 |

- **J1 は写しを使わない**（`SOURCES[JAP].mirror = false`）。写しの J1 は日付が dd/mm と
  mm/dd で揺れて JPN.csv と一致せず（2026-09-09 実測: 2022〜24 の 335 行が別の試合として
  残る）、2024-12 で止まっている。JPN.csv が 2012 年から完全なのでそれだけを使う
- 同じ試合の同一視は「Division・home・away が同じで日付が ±1 日以内」（時差で現地日付が
  ずれうる）。台帳の決済（`settle`）と同じ規則
- 取得元が全て落ちた日も前日までの履歴で予想は出る。その予想行には `historyAsOf`
  （学習に使った最新の試合日）と `historyMissing`（台帳が知る開始済みの試合で履歴に結果が
  無い数）が残り、後から鮮度を見分けられる。**取得元の 503 は `::warning::` で赤くしない**
  （2026-09-07 のフェイルクローズは「503 ページを CSV として読む」を防ぐためのもので、
  見出しの検査はそのまま。落ちる先が「止める」から「履歴で進む」に変わった）
- 履歴の初期化・再構築は `football.ts history-import`（写しと生 CSV を見出しで判別）。
  初期値は写し（2022-04〜2026-09-03）+ probe 2026-09-03 の 2526/2627 CSV + JPN.csv +
  台帳の results から作った（同じ試合の得点の食い違い 0 件）

### 取得物の検査（2026-09-07・2026-09-09 に「止める」から「履歴で進む」へ）
football-data.co.uk は 2026-09-06〜07 に Actions のランナーへ **HTTP 503 のエラーページ
（489 バイト）** を返した。旧実装は `curl -o` の終了コードしか見ておらず、それを CSV として
保存 → パーサは見出しが無いので 0 行 → 日次は「学習データ 0 件・results recorded 0」の
まま**緑で終わり**、2 日間 49 試合が決済されず、予想も 0 件だった（run #6・#7 の実測）。
- workflow は **HTTP 200 かつ見出しが `Div,` / `Country,` で始まるものだけ**を受理する
  （エラーページを CSV として読まない）。取れなかったファイルは cache に置かず
  `::warning::` を出して**続行**する（2026-09-07〜09 は 1 ファイル欠ければ全体を止めていたが、
  それでは取得元が落ちている間ずっと予想が出ない。上記「結果の取得元は 3 つ」）
- CLI（`updateHistory`）も `assertFootballDataCsv` で同じ検査をする（cache を手で置いた場合の守り）
- **緑を「取れた」と読まない**。判定はログの `ok <file> <bytes> via <host>`（2627 は 5〜20 KB・
  過去季は 100〜200 KB・JPN.csv は約 570 KB）、`<Div>: history N → M … latest <日付>
  missing <件数>`（missing = 台帳が知る開始済みの試合で履歴に結果が無い数。0 が正常）、
  `predictions.ndjson` / `results.ndjson` が実際に伸びたかで行う
- 取得元が全て落ちている間は結果が入らず決済も止まるが、予想は前日までの履歴で出る。
  台帳は追記専用なので、復旧後の日次が直近 30 日ぶんを取り直して決済する（欠落しない）

### 3 経路が同時に落ちた日と、沈黙の検知（2026-09-16〜17）
2026-09-16 から **3 つの取得元が同時に使えなくなった**。設計上「1 つ落ちても止まらない」
はずが、3 つ同時なら結果は 1 件も入らない。それでも日次は 2 回**成功で終わった**
（取得の失敗は `::warning::` で赤くしない設計のため）。9/15 以降の結果が入らず
`settled 0` が 2 日続いたことは、緑のログからは見えなかった。

| 取得元 | 2026-09-17 の実測 |
|---|---|
| football-data.co.uk | **37/37 失敗**。`HTTP 302` → 転送先が `127.0.0.1:80` で接続不能。両ホストとも同じ |
| GitHub の写し（xgabora） | 取得は成功（45 MB）だが**最終行が 2026-09-03**。2 週間遅れていて穴を埋められない |
| The Odds API `scores` | **残クレジット 5**。`< 40` のガードで必要な 3 競技すべて飛ばされた |

代替も測ったが**どれも鮮度が足りない**（2026-09-17 実測）: `openfootball/football.json` は
得点入りの最新が **2026-09-06**（en.1 / es.1 / it.1 とも 9/6〜9/7）で、写しと同じく
10 日以上遅れている。**無料で届く GitHub 上のミラーは、どれも一次情報の代わりにならない。**

入れた対策は 2 つ。**取得元そのものは直せない**（外部サイトの遮断）ので、直したのは
「気付けない」ことと「無駄に待つ」ことだけである。

- **沈黙の検知**（`src/health.ts` + `football.ts health`・workflow の最終ステップ）。
  VORTE EV の `ingest_health` と同じ考え方で、判断の前に生の事実を出す:
  「結果を最後に取り込んでから何時間か」と「開始済みなのに決済されていない予想」。
  **36 時間で警告・72 時間（日次 3 回連続で結果 0 件）で run を赤くする。**
  72 時間は VORTE EV の `archive-freshness` と同じ基準。
  判定に**バックログの古さを使わない**のは、実測（本番 155 決済）で決済ラグが
  中央値 13.9h・90%点 97.5h・最大 118.5h あり、正常な遅れ（〜5 日）と区別が付かないため。
  ステップは **commit の後**に置く。落として赤くしても、取れたぶんの追記は済んでいる
- **fail-fast と転送先の記録**（workflow の CSV 取得）。サイトが全滅している日に
  37 ファイル × 2 ホスト × 2 回を総当たりしても同じ失敗を 148 回繰り返すだけで、
  実測 **7 分 43 秒**かかっていた。先頭 2 ファイルが両ホストで落ちたら全滅と判断して
  残りを飛ばす（模擬障害で **20 秒**へ短縮・実測）。健全時と部分障害時に誤作動しないことも
  模擬で確認済み（37/37 成功・36/37 成功のいずれも fail-fast は作動しない）。
  併せて `%{redirect_url}` をログに出す。今回の 302 は Location がログに無く、
  原因の特定に本番ログのダウンロードが要った。`--proto-redir =https` を付けたので、
  `http://127.0.0.1` のような転送は追わずに落ちる

**復旧したら欠落は自動で埋まる**（台帳は追記専用で、日次が直近 30 日ぶんを取り直す）。

### 発行の沈黙を検知する（2026-09-22・Founder 承認 1-1）
2026-09-19〜22 に**4 日間まったく予想が発行されなかったのに、日次は毎回緑**だった。
結果の取込が 72 時間で赤くなる仕組みはあるのに、**商品そのもの（予想）が止まっても
何も鳴らなかった**。今回の事故の一番大きな教訓はここにある。

**台帳からは検知できない**（実測）。`recordFixtures` は内容が変わったときだけ追記するので、
「取得元が同じ日程を返した」と「取得元が何も返さなかった」は台帳上で区別が付かない。
実際、日程を書いた回の間隔は **中央値 53.9h・最大 103.9h** あり、ここに時間の閾値を
置くと平常運転でも鳴る。そこで**日次に 1 回分の実績を書かせる**:

- `football/reports/run.json` — リーグごとの「取得元が返した試合数 / 新規 / 発行 / 繰延 /
  封緘前」と、**日程 0 件の回が何回続いているか**
- `health` がこれを読み、次の 2 つで赤くする
  1. **日程 0 件が 2 回連続**（`ZERO_FIXTURE_FAIL_RUNS`）
  2. **取りこぼし**＝封緘より前に台帳へ入っていたのに、封緘を過ぎても予想が無い試合

**2 回にしたのは実測の結果。** 事故を再現すると在季の 0 件は **9/19 と 9/20 の 2 回で
止まった**（9/21 以降は国際試合週間で次のキックオフが 18 日先になり「季が動いていない」
扱いになる）。**3 回にすると事故そのものを取り逃がす。**

- **「そもそも仕事が無かった」は数えない**（`seasonLive`）。3 日以内にキックオフする試合が
  台帳に無い回は 0 件でも数えない。国際試合週間・オフシーズンで赤くしないため。
  VORTE EV の `expected_24h` と同じ役割
- 取りこぼしは**封緘後に初めて登録された試合を除く**（無料の fixtures.csv は約 3 日先まで
  しか載らず、当日登録が起こりうる）。**学習データに無いチーム**（昇格直後）も判定に使わない
- **記録開始日 `PUBLISH_HEALTH_START` より前の取りこぼしは報告するが赤くしない。**
  導入時の実測で **2026-09-13 封緘の 31 件が既に取りこぼされていた**（日次が 9/12 23:55Z の
  次は 9/14 00:04Z で、**9/13 の回が存在しない**。原因は未特定・UNKNOWN）。過去の分で
  赤を出し続けると新しい取りこぼしが埋もれる

実測（2026-09-22）:

| 検証 | 結果 |
|---|---|
| 事故の再現（取得元が何も返さない 9/19・9/20・9/21） | 9/19 は黄 → **9/20 で赤（exit 1）**。事故の 2 日目で気付ける |
| 本番相当（復旧後の実 cache・9/23 の回） | **緑**。日程 81 件・取りこぼし 0 件・記録開始前 10 件は参考表示のみ |

### 沈黙を数える前に「取り込むべき試合があるか」を見る（2026-09-25・Founder 承認）
結果の取込の警報は「最後に結果を書いてから何時間経ったか」だけを見ており、
**そもそも試合があったかを見ていなかった**。導入時の「毎日どこかのリーグで試合がある」
という前提が誤りで、**国際試合週間は 10 リーグが同時に止まる**（2026-09-22〜10-09 は
17 日間 1 試合も無い）。放置すると日次が 2 週間赤くなる。

実測で見ると、前提の誤りはもっと前から出ていた。**健全に動いていた期間の取込間隔**は

| 区間 | 間隔 | 現行 72h 判定 |
|---|---|---|
| 09-04 07:54 → 09-09 15:32 | **127.6h** | fail |
| 09-15 00:29 → 09-18 00:06 | 71.6h | warn |
| 09-18 00:06 → 09-22 00:43 | **96.6h** | fail |
| 中央値（全 11 区間） | 24.4h | ok |

つまり **72h の閾値は平常運転でも鳴っており、鳴っても故障と区別が付かなかった**。

VORTE EV の `expected_24h`（NPB の月曜休養日）と同じ形で、**判断を足すのは `health` 側**にする。
生の事実（`hoursSinceRecord`）は `ingestHealth` にそのまま残す。

- `ingestDue(matches, lastRecordedAt, now)` — **最後の取込より後にキックオフし、
  猶予を過ぎた試合**の最古の 1 件。無ければ null＝沈黙は期待どおり。
  最後の取込より後に始まった試合の結果は**定義上まだ台帳に無い**（書き込みはキックオフより
  前に終わっている）ので、結果との照合は要らない
- `RESULT_DUE_HOURS = 120`。実測（日次が回り始めた 2026-09-10 以降の 189 件・
  キックオフ日 00:00Z から取込まで）は **中央値 48.7h / p95 96.3h / 最大 111.5h**。
  取得元の CSV が週明けにまとめて更新されるため **4 日以上かかるのは異常ではない**。
  111.5 をそのまま書かないのは標本 189 件に対して精度を詐称しないため。
  この猶予で**上表の誤警報は 0 件になる**（実測）
- **検知は遅くなる**（取得元が全部落ちた場合、気付くのは試合日から 5 日後）。
  それでも旧実装より良い。旧実装の 72h は平常運転の間隔を下回っていた
- `health` は理由を必ず出す。`沈黙は期待どおり: 結果が出ているはずの未取込の試合は 0 件
  （猶予 120h）・次の試合 …` / `未取込の最古: N1 …（…h 前・猶予 120h）`。
  「何も来ていない」と「来るはずのものが無い」を取り違えないため

### 日程が動いた試合を決済する（2026-09-25・Founder 承認）
決済は **league + 両チーム + 日付 ±1 日**でしか結んでいなかったため、延期・前倒しされた
試合は**結果が自分の履歴にあるのに永久に決済されず、静かに記録から落ちていた**。
「全件記録して見せる」が崩れる。本番で詰まっていた 3 件は、実は 3 つとも別の話だった:

| 試合 | 予想した日 | 実際 | 正しい扱い |
|---|---|---|---|
| N1 Utrecht v Go Ahead Eagles | 09-05 | **09-08 に 3-3** | 延期。**決済する** |
| SP1 Sevilla v Valencia | 09-13 | 09-11 の 1 試合だけ（09-11 の予想が決済済み） | **幽霊日程。決済しない** |
| SP1 Levante v Ath Bilbao | 09-16 | 9 月の結果がどこにも無い | **UNKNOWN。決済しない** |

**窓を広げるだけでは 1 試合を 2 回数える。** Sevilla v Valencia は取得元が同じ試合を
09-11 と 09-13 の 2 つの日程として返しており（どちらも 09-03 に同じ取得で登録）、
素朴に広げると 09-11 の結果で 2 回決済される。よって `settle` は 2 段構えにした。

1. **1 段目（従来どおり）**: 日付 ±1 日
2. **2 段目**: `RESCHEDULE_WINDOW_DAYS = 21` まで窓を広げる。ただし
   - **ほかの予想が ±1 日で取れる結果は候補から外す**（それはその予想のもの）
   - **同じカードの未決済がほかにもあれば結ばない**（どれがどれか決められない）
   - 候補がちょうど 1 件のときだけ結ぶ。それ以外は決済しないまま残す（フェイルクローズ・
     推測で埋めない）

窓を 21 日で切るのは、SC0 のように**同じ並びの対戦をシーズン中に複数回やるリーグ**で
別の試合に食い付かせないため。

決済行に `resultDate` と `matchedBy`（`kickoff` / `rescheduled`）を残す。
**どの結果で決済したかを行だけで検証できる**ようにするためで、
2026-09-25 以前の行には無い（台帳は追記専用なので既存行は書き換えない）。

本番台帳に対する実測（**VERIFIED**・書き込みは写しに対して実施）:
**決済 1 件（258 → 259・Utrecht v Go Ahead Eagles 3-3・RPS 0.146）**、
2 回目は 0 件（冪等）、**既存 258 行は md5 一致で不変**、
`predictions` / `matches` / `results` も不変。幽霊日程と結果なしの 2 件は未決済のまま。

### B1 / SC0 / JAP に無料の第 2 経路は見つかっていない（2026-09-22・Founder 承認 1-3）
「ベルギー・スコットランド・J1 は `.org` の無料枠の対象外」は推測のままだったので、
トークンで実際に読める大会を取って**事実にした**（probe 2026-09-22T07:40Z）。

**読めるのは 13 大会**: `BSA` `ELC` `PL` `CL` `EC` `FL1` `BL1` `SA` `DED` `PPL` `CLI` `PD` `WC`。
**B1（ベルギー）・SC0（スコットランド）・JAP（J1）は無い**（推測どおりだったが、これで確定）。
なお `ELC`（イングランド 2 部・football-data の `E1`）は読める。今は対象外だが、
リーグを増やすなら結果の経路は既にある。

鍵の要らない公開 JSON（openfootball）も測った:

| URL | 結果 |
|---|---|
| `football.json/master/2026-27/en.1.json` | **200**（54,951 バイト） |
| `football.json/master/2026-27/de.1.json` `it.1.json` | **200** |
| `belgium/master/2026-27/be.1.txt` | **404** |
| `scotland/master/2026-27/sco.1.txt` | **404** |
| `japan/master/2026/jp.1.txt` | **404** |

**3 リーグとも綴りが当たらなかった。** 404 は「その綴りが無い」であって「情報源が無い」
ではないので、**別の経路があるかは UNKNOWN のまま**。推測で実装しない。
現状この 3 リーグの結果は **football-data.co.uk が単一経路**で、そこが凍ると決済が止まる
（2026-09-22 時点の決済待ち 13 件のうち 9 件が J1 なのはこれが理由）。

### fixtures.csv だけで日程を賄えるかは未測定（2026-09-22・Founder 承認 1-2）
The Odds API（無料 500/月）への依存を切れるかを測ろうとしたが、**国際試合週間で測れない**。
9/22 07:40Z に取った fixtures.csv は 198 行あるが**すべて 18〜20/09 の過去分**で、
今後の試合が 1 件も載っていない（次節は 10/09）。

今ある唯一の手がかりは 2026-09-02 の probe で、**取得日 +1 日**までしか載っていなかった
（fetched 09-02 / 収録 09-01〜09-03）。日次は 00:04Z、封緘はキックオフ前日の 11:00Z なので、
**+1 日でも理屈の上では間に合う**（翌日の試合を、その前日の回で発行できる）。ただし**余裕が
ゼロ**で、日次が 1 回飛ぶと翌日の試合は発行できなくなる。The Odds API はその余裕を

**結論: いまは The Odds API を外さない。** 季が戻る 10/09 以降に fixtures.csv の収録範囲を

#### チーム名は推測で寄せない（ここが一番危ない）
取得元ごとに表記が違う（co.uk「Man United」/ .org「Manchester United FC」）。

   片方へ寄せない）

## 予想モデル（dc-v5-shots・2026-09-22）

正準は **`dc-v5-shots`** = `dc-v3-decay`（Dixon-Coles・ξ=0.002・窓 1500 日・L2 罰則 α=2）に
**枠内シュート層（θ=0.25）**を足したもの。

### 枠内シュート層（2026-09-22・Founder 指示「xG を実装」への回答）
**xG そのものは実装していない。** 1 本ごとの質を出すには有償か規約の怪しい取得元が要る
（Understat / FBref は probe で到達性だけ見て、規約未確認のまま止めてある）。一方、
**我々が毎日落としている football-data.co.uk の結果 CSV には枠内シュート（`HST` / `AST`）が
元から入っていた**（実測: 9 リーグ × 4 季で欠測 0）。追加の取得元も鍵も課金も要らず、
規約上も自由に使える。まずここから測った。

やり方: 同じ Dixon-Coles を**枠内シュートの本数**にも当てはめ（低スコア補正 ρ は枠内
シュートには意味が無いので切る）、得られた λ を**学習窓内の決定率**（得点合計 / 枠内
シュート合計）で得点尺度へ直し、得点由来の λ と `(1−θ):θ` で混ぜる。
**決定率は学習窓の中だけ**から計算する（未来の試合を混ぜない）。

実測（probe の 4 季・9 リーグ・**6,416 試合**のウォークフォワード。選定は 2025-08-01 まで、
検証はそれ以降）:

| θ | 選定期間 RPS | 検証期間 RPS | 検証の差 | t |
|---|---|---|---|---|
| 0（従来 dc-v3-decay） | 0.2007 | 0.2004 | — | — |
| 0.15 | 0.1999 | 0.1999 | −0.00048 | −3.62 |
| **0.25（採用）** | 0.1995 | **0.1997** | **−0.00070** | **−3.16** |
| 0.35 | 0.1992 | 0.1996 | −0.00084 | −2.69 |
| 0.55 | 0.1989 | 0.1996 | −0.00086 | −1.75 |

**選定期間だけなら θ=0.55 が最良だが、それはグリッドの端で検証期間では有意にならない**
（過学習の典型）。検証済みの平坦域の中央として **0.25** を採る。

**市場には勝てない（重要）。** 同じ 6,416 試合で市場は **0.1946**。対数オッズで結合しても
**モデルを足した効果は −0.00003**（モデルの係数は −0.1 と負のまま）。**枠内シュート層は
モデル単独の質を上げるだけで、市場を超えるエッジにはならない。** ページが確率だけを出し、
EV も賭けの推奨も出さない方針は変わらない。

- **J1（JAP）には効かない。** `JPN.csv`（football-data の「追加リーグ」形式）にはシュートの
  列が無い（実測 0 列）。層が作れない試合は**得点だけのモデルへ落ち**、予想行の
  `shotWeight` に 0 を残す（使ったことにしない）
- 履歴は `sot` を持つようになった。**co.uk 同士は優先度が同じで得点も同じだと置換されない**
  ため、既存行に枠内シュートが一生入らない。`mergeHistory` に「欠けている列だけを足す」
  経路（`enriched`）を入れた。適用時の実測: 9 リーグで **67〜75%** の行が枠内シュートを得た
  （落としている 4 季ぶん。学習窓 1500 日のほぼ全体を覆う）
- **θ=0 にすれば `dc-v3-decay` と 1 ビットも変わらない**（テストで固定）

### 土台（dc-v3-decay・2026-09-17）


ξ・窓・α の根拠は以下（`dc-v5-shots` もこの設定をそのまま使う）。
**挙動が変わったらモデル名を必ず変える**（台帳で新旧の予想を混同しないため）。
台帳の予想行は `model` / `ridge` / `xi` に適用値を持つ（`dc-v1` の行には `ridge` が、
`dc-v2-ridge` 以前の行には `xi` が無い。追記専用なので既存行は書き換えない）。

### なぜ時間減衰を変えたか（2026-09-17 の実測）
**ξ=0.0065（半減期 107 日）は Dixon-Coles 論文の既定値を引き継いだだけで、このデータで
一度も調整していなかった。** α=2 を決めたときも ξ は固定していたので、両者の相互作用も
測っていない。今回 ξ × α を同時に振った。

全 10 リーグ・2015 年以降 33,642 試合のウォークフォワード・**同一試合集合のペア差**
（現行 ξ=0.0065 / α=2 が基準。負ほど良い）:

| ξ | 半減期 | RPS 差（α=2） | t |
|---|---|---|---|
| 0.0015 | 462 日 | −0.00184 | −7.51 |
| **0.002（採用）** | **346 日** | **−0.00193** | **−9.09** |
| 0.0025 | 277 日 | −0.00191 | −10.48 |
| 0.003 | 231 日 | −0.00179 | −11.69 |
| 0.0045 | 154 日 | −0.00115 | −14.56 |
| 0.0065（従来） | 107 日 | ±0 | — |
| 0.009 | 77 日 | +0.00151 | +19.80 |
| 0.012 | 58 日 | +0.00326 | +22.05 |

- **10 リーグ全てで同じ向き**（リーグ別でも t=−2.6〜−5.3）で、かつ単調。従来値は最適域の外
- 効果 −0.0019 は**モデルと市場の差（約 0.0072）の 4 分の 1**
- **過学習ではない**: 2015-2021 だけで選ぶと ξ=0.002 が選ばれ、選定に使っていない
  2022-2026 で測り直すと −0.00208（t=−6.14）とむしろ僅かに良い
- α は 2 のまま。どの ξ でも α=5 は α=2 に劣る。最小確率 <5% の予想は 1.7% → 1.8% でほぼ不変
- **窓は 1500 日のまま据え置いた**。ξ=0.002 では窓の端に重みが e^-3 ≈ 5% 残るため、
  窓 3000 日にすると**さらに −0.00009 良くなる（t=−5.10・実測）**。ただし今回の改善の
  4.5% しかなく、履歴の保持を倍にする代償（再取り込み・学習時間）に見合わない。
  平坦な最適域では継承値からの変更を最小にする。取り込みが安定してから別途扱う
- 結線は `test/canonical-model.test.ts` が文字列で固定する（**設定を変えたらモデル名も
  変わること**と、`fitDixonColes` に ξ / α を明示して渡していること）。日次の設定は
  定数リテラルにしか存在せず、型検査もテストも素通りするため

### なぜ正則化を入れたか（2026-09-15 の実測）
`fit.ts` の最尤推定に攻撃力・守備力の正則化が無く、チーム個別のパラメータが発散していた。
実際に発行された予想に **λ=0.025（40 試合に 1 点）や λ=4.835** が出ており、
「最小確率 1%」のような予想が 168 件中 7 件（4.2%）あった。

対策は攻撃力・守備力を **リーグ平均へ** 縮小する L2 罰則（階層ベイズの MAP 近似）。
**0 へではなく平均へ縮小する** — 識別性の制約は `Σattack=0` だけで、守備力の平均は
リーグ全体の失点水準を担っている。0 へ縮小するとその水準ごと下げてしまう。

実測（全 10 リーグ・履歴 11,116 予想のウォークフォワード・`warmup 300 / window 1500d`）:

| α | RPS | α=0 との差 | 最小確率 <5% の予想 |
|---|---|---|---|
| 0（従来） | 0.2036 | — | 4.3% |
| **2（採用）** | **0.2021** | **−0.0015（t=−5.02）** | **1.3%** |
| 3 | 0.2023 | −0.0013 | 0.8% |
| 10 | 0.2064 | +0.0027（悪化） | — |
| 50 | 0.2197 | +0.0161（悪化） | — |

10 リーグ中 9 で α=2 が最良、E0 のみ同値（悪化したリーグは無い）。J1 だけは α=5 が最良。
α=3 は RPS の差が雑音以下で極端予想はさらに減るので、**極端予想が再発したときの次点**。

### 既知の限界（重要）
**正則化はモデルを市場に追いつかせない。** 同じ 11,085 試合で市場（オッズの含意確率）と
対照すると、モデルは **α=0 で +0.0088・α=2 で +0.0072 だけ市場より悪い**（t=13.65）。
市場との乖離が大きい群ほど成績が悪いという関係も残っている（乖離 20pt 以上の 167 件では
α=2 でも +0.0495）。**つまり乖離は依然としてエッジではなく雑音**であり、
この状態でハンデの EV を計算してはいけない（推奨が最も外している試合に集中するため）。

着手前の見積もりでは「極端予想を直せば市場との差の 94% が埋まる」としていたが、
これは決着 151 件の標本からの外挿で **誤りだった**。11k 試合では乖離 20pt 以上は
全体の 1.5%（167 件）しかなく、そこを直しても全体の平均はほとんど動かない。
差を埋めるには市場ブレンドか xG のような別の手段が要る。

### 予想を出す範囲（2026-09-16・Founder 指示「海外リーグの試合は全て予想を出力」）
日次は**キックオフまで 720 時間（30 日）以内**の未予想の試合を全て発行する
（`HORIZON_HOURS`）。学習窓の中での試合数が **1 試合以上**あるチーム同士なら発行する
（`MIN_TEAM_MATCHES`）。変更前は 48 時間 / 5 試合で、台帳の日程 107 件のうち
予想が出ていたのは 6 件だけだった。

2 つの歯止めを緩める前に、それぞれの代償を実測した（全 10 リーグ・履歴のウォークフォワード・α=2）。

**早く出しても精度は落ちない**（キックオフの何日前の情報で出すかを振った）:

| 出す時点 | RPS |
|---|---|
| 0 日前（従来） | 0.2021 |
| 3 日前 | 0.1998 |
| 7 日前 | 0.2030 |
| 14 日前 | 0.2019 |

差は最大 0.0023 で単調ですらなく、雑音の範囲。時間減衰の半減期が 107 日なので
1〜2 週間ぶんのデータ増減がほとんど効かない。30 日で頭打ちにするのは、日程の
取得元が遠い将来の試合を返し始めたときの歯止め（台帳の実測は最大 26 日先）。

**標本の薄いチームは、むしろ極端な予想を出さない**（少ない方のチームの試合数で層別）:

| 学習窓での試合数 | n | RPS | 最小確率 <5% |
|---|---|---|---|
| 1–2 | 98 | 0.2100 | **0.0%** |
| 3–4 | 94 | 0.2029 | 1.1% |
| 10+ | 10,703 | 0.2021 | 1.3% |

閾値 5 の根拠は「標本が薄いと確率が極端になる（20 試合で 98/2/0 を実測）」だったが、
その病理は正則化そのもので直っており、平均へ縮小される薄いチームは逆に極端になりにくい。
精度は 1–2 試合でやや落ちるが病的ではない。各予想行に `nTeamMin`
（両チームのうち少ない方の試合数）を記録するので、**後から層別して測り直せる**。
1 未満には下げない — 学習に 1 度も出ていないチームは `predictMatch` が例外を投げる
（中立値で埋めない）。

### 無料の市場オッズ = football-data の fixtures.csv（2026-09-19）
The Odds API の無料枠（500/月）は構造的に足りない。オッズだけで月 300、`scores` が
約 180、さらに野球側（`odds.yml`）も同じ鍵を使う。**クレジット配分の最適化は実測で
効果が無かった**（「近い試合があるリーグだけ取る」案はシーズン中どのリーグも毎週試合が
あるため月 300 → 270 にしかならない。3 日以内まで絞ってこれで、日程の取りこぼしリスクに
見合わない）。つまり**コードでは解決できない**。

そこで**無料で無制限に取れる第 2 の市場**を入れた。`football-data.co.uk/fixtures.csv`
（今後の試合 + 各ブックのオッズ）で、**結果 CSV と同じホスト**なので鍵も課金も要らない。
リポジトリ内の実サンプル（`lib/football-model/fixtures/fd-fixtures.csv`・probe 2026-09-02）
で測った実測:

| 項目 | 実測 |
|---|---|
| 収録範囲 | 今後 **約 3 日先**まで |
| ブック | B365 / BFD / BV / BW / PP / SKB の 6 社 + Max + Avg（94 列） |
| オッズのある行 | **48/48** |
| チーム名 | 台帳と **22/22 一致**（対応表は要らない） |
| **J1（JPN）** | **収録なし（0 行）**。football-data の「追加リーグ」は載らない |
| パーサ | `footballDataRaw.ts` に**既に実装があり、使われていなかった** |

- 市場は **The Odds API を優先し、無ければ fixtures.csv で補う**。どちらから採ったかは
  予想行の `marketSource`（`odds-api` / `football-data`）に残す。
  2026-09-18 以前の行には無く、すべて `odds-api`
- **確率の作り方は両者そろえる**（`footballDataFixtures.ts`）: 各ブックのオッズを逆数化して
  1 に正規化（控除率をブックごとに抜く）→ 結果ごとに中央値 → もう一度正規化。
  `Avg`（各社オッズの平均）は使わない。**オッズの平均と確率の中央値は別物**で、
  取得元で作り方が違うと市場ベンチマークの比較が壊れる
- 収録が約 3 日先までという範囲は `MARKET_GRACE_HOURS`（48 時間）と噛み合う。
  **封緘の直前には必ず収録範囲に入っている**
- 実測（台帳の実試合 40 件で fixtures.csv を組み、The Odds API 不在で日次を実行）:
  40 件に `marketSource=football-data` が付き、市場なしの封緘は **122 → 29 件**。
  実運用では fixtures.csv がキックオフ 3 日前までを覆うので、さらに減る

#### 市場だけでは足りなかった — 日程も第 2 経路を持つ（2026-09-21・実発生）
上の対策を入れても **2026-09-19〜21 の 3 日間、新しい予想が 1 件も出なかった**（実測・
台帳の予想は 299 件で止まっていた）。原因は、無料の fixtures.csv を**市場の第 2 経路**
としてしか結線していなかったこと。**「どの試合があるか」は The Odds API だけが持って
いた**ため、クレジットが 0 になった日に日程そのものが台帳へ入らず、発行対象が 0 件に
なっていた（日次のログは毎回「odds が無い（予想は発行しない）」で終わっていた）。

- `fixturesAsMatches()` が fixtures.csv を**日程の取得元**としても使う。The Odds API を
  先に入れ、そのあと無料の日程で埋める
- **キックオフは英国現地時刻からの変換**。`Date` / `Time` 列は英国時間（夏時間あり）で、
  固定のずれを足すのではなく Europe/London の実際のずれを引く（`ukLocalToUtc`）。
  **実測で検証済み**: probe 取得の fixtures.csv 198 行のうち、The Odds API 由来で台帳にも
  載っている **81 件すべてが分単位で一致**（81/81）。ここがずれると封緘（キックオフの
  JST 日付の前日 20:00）が丸一日ずれるので、規則を変えたらこの突合をやり直すこと
- **providerId は合成する**（`fd:<リーグ>:<ホーム>:<アウェイ>:<現地日付>`）。台帳は
  providerId で試合を同定するので、同じ試合が両方から入ると**1 試合に 2 つの予想**が
  立ちうる。`Ledger.recordFixtures` の**正準重複検査**（リーグ・両チーム・キックオフ
  ±1 日が一致する別 ID があれば捨てる）が防ぐ。どちらが先に入っても結果は同じ。
  適用時の実測: 既存 333 試合に正準重複 0 件（既存の挙動を変えない）
- 実測（2026-09-21・実台帳の写しで検証）: 実台帳に対して走らせると fd 由来 81 件は
  すべて「重複」で捨てられ、**4 ファイルとも md5 が不変**。日程を空にした台帳では
  **81 件が登録され 81 件の予想が発行**（市場は 81/81 が `football-data` 由来・欠測 0）
- **既知の限界**: fd 由来の ID で登録された試合は、後から The Odds API が同じ試合を
  返しても市場スナップショット（`football/market/`）が別 ID で積まれるため、決済時の
  「直前の市場」と CLV の対象から外れる。発行時点の市場は入るので RPS の対照は残る
- **J1（JAP）は fixtures.csv に無い**ので、この経路でも日程は入らない（下記のとおり
  対象から外している）

#### J1 を対象から外した（2026-09-19・Founder 判断「対象リーグを減らす」）
`soccer_japan_j_league` の**オッズ取得だけをやめた**（月 30 クレジットと J1 ぶんの
`scores` が浮く）。理由は 2 つ:
- **無料の fixtures.csv に J1 が無い**（実測 0 行）。市場を持つには有料枠を使うしかない
- モデルの成績が 10 リーグで最も悪い（RPS **0.2896** 対 他はおおむね 0.20 前後）

**台帳からは消さない。** 登録済みの J1 の試合は予想も決済も従来どおり続き、新しい日程が
入らなくなることで自然に終わる。戻すときは workflow の競技一覧へ 1 行足すだけでよい。

### 市場が無い日に大量封緘しない（2026-09-18 の実発生）
Odds API のクレジットが尽きてオッズが 1 件も取れなかった日に、発行範囲 720 時間
（2026-09-16 に 48h から拡大）の効果で **122 件が一度に `market: null` のまま封緘された**。
市場ありの割合は **97% → 58%** へ落ちた。予想は 1 試合 1 回で書き換えないので、
**その試合の発行時点の市場は永久に欠測する**。

拡大前は 1 日に数件しか発行しなかったため、同じ 1 日の障害で失うのは数件だった。
**発行範囲の拡大と取得元の障害が噛み合って被害が 20 倍以上になった**のがこの事故である。

対策は `MARKET_GRACE_HOURS = 48`。**市場が取れていない試合は、封緘まで 48 時間を切るまで
発行を待つ。** 市場が取れている試合は従来どおり即発行する（待つ理由が無い）。

- 48 時間は拡大前の発行範囲そのもの。日次が 1 回飛んでも封緘前にもう 1 回走る余裕がある
  （このアカウントの schedule は実測で 4〜5 時間遅れて着地するため、余裕は要る）
- **「予想は試合前に必ず出す」（Founder 指示 2026-09-09）は不変**。取得元の生死と発行を
  切り離す設計は変えていない。繰り延べた試合も封緘前に必ず出る。実測で確認済み:
  9/18 の状態を再現して 9/19〜9/21 の回まで回し、**封緘を過ぎたのに予想が無い試合 0 件**
- 事故当日で再現すると発行は **122 → 69 件**。残る 69 件は封緘が 11 時間後に迫っており、
  上の指示どおり出すべきもの
- **決済側のベンチマークは失われない**。2026-09-17 以降、決済は `football/market/` の
  スナップショットから「キックオフ直前」を引く（上節）ので、後日オッズが復旧すれば
  そちらは埋まる。永久に失われるのは発行時点の市場と、それを使う CLV だけ
- ガードは `test/canonical-model.test.ts` が固定する（消すとテストが落ちる）

### 市場は「直前」で対照する・CLV（2026-09-17）
予想行の `market` は**発行時点**の市場である。2026-09-16 に発行範囲を 48 → 720 時間へ
広げた結果、オッズが先まで出るリーグは**キックオフの 3 週間以上前に封緘**されるように
なった（実測: E0 / I1 / D1 / F1 は 25.8 日先までオッズが返る。B1 / N1 / P1 / SC0 / JAP /
SP1 は約 4 日先まで）。予想は 1 試合 1 回で書き換えないので、市場値も 3 週間前のまま固定される。

市場はキックオフに近いほど良い（**同一試合集合**での実測・2026-09-17）:

| スナップショットの時点 | n | 市場 RPS | 直前比 |
|---|---|---|---|
| 0-1 日前（直前） | 151 | 0.2010 | — |
| 1-3 日前 | 146 | 0.2027 | +0.0002 |
| 3-7 日前 | 109 | 0.2012 | +0.0004 |
| 7 日以上前 | 49 | 0.1981 | +0.0051 |

差は単調でなく n=49 では有意でもない（t=1.38）が、符号は一貫して「古いほど悪い」で、
大きさ（+0.005）はモデルと市場の差（約 0.009）の半分に達する。発行が 3 週間前になった今、
発行時点の市場だけで対照し続けると**ベンチマークが古い市場に固定され、モデルを不当に
良く見せる**。よって決済では**キックオフ直前の最新スナップショット**でも RPS を測る。

- 実装は `src/marketSnapshots.ts`。**新しい台帳ファイルは作らない**。`football/market/` は
  取得ごとに 1 ファイルの追記専用で、それ自体が時系列である（CLAUDE.md の二重管理の禁止）。
  ここはその索引を作るだけ
- **キックオフ以降のスナップショットは使わない**。試合が始まった後のオッズは試合内容を
  織り込んでおり、予想の対照に使えば後知恵になる（境界も含めてテストで固定）
- 決済行に `marketRpsClosing` と `marketClosingFetchedAt` が増えた。**2026-09-17 以前の行には
  無い**（台帳は追記専用・既存行は書き換えない）。スナップショットが無い試合は null で、
  推測では埋めない
- `reports/summary.md` の「市場 RPS（直前）」列は、**その列の試合集合だけ**で発行時点との差を
  セル内に持つ。左の「発行時点」列は全決済が母数なので、**2 つの市場列を横に比べてはいけない**

#### CLV（Closing Line Value）
モデルが「市場より高い」と見た結果について、市場が発行時点からキックオフ直前までに
こちら側へ動いたかを測る（`src/clv.ts`・`football.ts clv`）。動いていれば、モデルは市場が
後から織り込む情報を先に持っていたことになる。**1 試合ごとの勝ち負けの運に左右されない**ので、
少ない標本でもエッジの有無を早く判別できる。

**実測（2026-09-17・決済済み 151 件）: 平均 +0.16pp・正方向 82/151（54%・95% [46%, 62%]）・
t=+1.85。** 符号は正だが、野球側 VORTE EV の同じ器での実測（+1.41pp・正方向 68.5%）の
**約 1/9** で、有意ではない。RPS の対照（同集合でモデル 0.2098 対 市場 0.2010）と整合し、
**このモデルに市場を超えるエッジがあるとは言えない**。上の「既知の限界」は変わらず、
ハンデの EV は計算しない。リーグ別の内訳は n=7〜20 しかないので**行の数字は読まない**。

## ハンデ清算表 SOCCER_LADDER_V1（2026-09-15・Founder 提供）

出典は Founder の「サッカーハンデ早見表」。実装は `lib/football-model/src/handicap.ts`、
全マスのゴールデンベクタは `test/handicap.test.ts`。指紋
`691e4c0147cbd393e32e1e37d0d985c81330cde1d5429923d2832c36e2333b53` を凍結してあり、
**1 マスでも変わるとテストが落ちる**。

### 野球の表を流用してはならない
Founder の明示「野球とサッカーのハンデ計算式は全く別物。野球の応用がサッカー」。
実装を突き合わせた結果、決定的な差は **0 台の刻み**にあった:

| 表記 | 野球 `0.3`（CUSTOM_TABLE_V1） | サッカー `0/3` |
|---|---|---|
| 引き分け m=0 | 30% 負け | 30% 負け（同じ） |
| 1 点差勝ち m=1 | **70% 勝ち** | **100% 勝ち** |

野球の `0.d` は m=0 と m=1 の 2 つに跨がるが、サッカーの `0/d` は**引き分けだけ**に効く。
また `0半` `2.x` `2半` は野球の定義域（31 表記）に無い。

### 構造は一本の梯子
常にただ 1 つの得点差だけが中間の係数を持ち、その上下は丸勝ち・丸負け。刻みは 1/10。

```
0/0 → 0/1…0/9 → 0半 → 0半1…0半9 → 1 → 1.1…1.9 → 1半 → 1半1…1半9 → 2 → …
```

- **A 型**（`k` `k.d` `0/d`）: 係数を持つのは m=k、値は −d/10（d=0 で勝負無し）
- **B 型**（`k半` `k半d`）: 係数を持つのは m=k+1、値は +(10−d)/10（d=0 で丸勝ち）

「1半」は 1.5 ではない。正規化は絶対禁止。勝負無しで `-0` を返さない
（`Object.is` で 0 と区別され、突き合わせが静かに狂うため）。

### 早見表で直接確認した表記
`VERIFIED_NOTATIONS` の 27 種（`0/0`〜`0/9` / `0半` `0半3` `0半5` `0半7` / `1` `1.3` `1.5`
`1.7` / `1半` `1半3` `1半5` `1半7` / `2` `2.3` `2.5` `2.7` / `2半`）。
梯子の規則はこれ以外（`0半1` や `3半` 等）にも及ぶが、**表で直接見たのはこの 27 種だけ**
なので、厳密に運用する呼び出し側は `isVerifiedNotation()` で絞ること。

### ハンデを貼り付けて、その試合だけの予想を出す
Founder 依頼（2026-09-06）。形式は野球側の一括貼り付けと同じで、空行区切り・`<>` が
ハンデを出している側。

```

```

```
アトレティコ・マドリード<0半5>
2時00分
オサスナ
```

- 日本語のチーム名は `teamNamesJa.ts`（184 名）で台帳の英語表記へ解決する。
  **対応表に無い名前は推測で埋めず未解決として残す**。同一クラブの別綴り
  （`Machida` / `Machida Zelvia` 等）は候補を複数返し、その日の対象試合に実在する方を採る
- **解析・解決に失敗したカードも理由つきで全件出す**。「提示されたのに記録に入らなかった
  ハンデ」を数えられないと記録の意味が失われる（野球側で 2026-08-07 に同じ轍を踏んだ）
- 上限は貼り付け 20000 文字・カード 200 件

ここにあるのは決済（結果が出た後の取り分）の規則だけで、EV も推奨も含まない。
EV 層はモデルが市場に並ぶまで着手しない（上記「既知の限界」）。手数料の扱いも未定
（野球側は勝ち 0.9 掛けだが、サッカーで同じかは **UNKNOWN**・推測で入れない）。

## 公開ページ（VORTE FT）の生成（2026-09-23・リポジトリへ移設）

Founder が毎日見る 1 枚の HTML。生成器は **リポジトリの中**にある。

```

  --ledger football/ledger --out <出力先>.html \
```

- **台帳を読むだけで、一切書かない。** 入力は `football/ledger/` の 3 ファイル
